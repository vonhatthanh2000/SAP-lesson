Trace a RAP request

Your first interview-level skill is not writing RAP syntax. It is predicting which artifact receives a request, which contract governs it, and when data becomes durable.

The tangible win

By the end, you can trace one Release Order action from a Fiori elements screen to persistence and back—and explain why each layer exists.

This directly supports the mission in MISSION.md and is the first gate in the one-month roadmap.

Build the model from the database outward

1. Data model

CDS entities give data business meaning and define the business-object topology. A root plus composed items creates the aggregate you change consistently.

2. Behavior contract

The behavior definition declares what consumers may do: create, update, delete, actions, draft, locks, authorization, validations, and determinations.

3. Consumer projection

A projection exposes the subset and behavior appropriate to a use case. It prevents the reusable domain model from becoming the UI's accidental public contract.

4. Service exposure

A service definition selects exposed entities. A service binding attaches a protocol and service category, such as an OData V4 UI service.

5. Client

Fiori elements interprets service metadata and annotations. It is a consumer of the business object; it is not the owner of business invariants.

The official anchors are SAP's RAP overview, business-object contract, service definition, and service binding.

Trace “Release Order”

Fiori elements→ OData V4 binding→ projection contract→ BO action→ transactional buffer→ save sequence→ persistence
  1. The client invokes the projected Release action through OData.
  2. The RAP runtime resolves the business-object instance and enforces the declared behavior contract.
  3. Authorization and feature control answer different questions: “may this user do it?” and “is it currently possible for this instance?”
  4. The action implementation requests the status transition in the transactional buffer. Related validations, determinations, and messages participate according to their declared triggers.
  5. The save sequence makes accepted changes durable; failures and messages return through the service to the client.

RAP's transaction is more than table CRUD: changes pass through a defined interaction and save contract. EML exposes the same BO operations locally from ABAP without routing through HTTP; see SAP's EML documentation.

Placement drill

Answer aloud before opening each explanation.

An item amount must change whenever quantity or unit price changes. Where does the rule belong?

A determination owns the derived value. It must be safe when triggered repeatedly; the UI may additionally need a side effect so it knows which values to reread. SAP notes that determination execution order is not fixed and determinations must be idempotent: Determinations.

An order with no items must not activate. Where does the rule belong?

A validation protects the invariant and reports a failure/message. Hiding an Activate button would not protect EML or other non-UI consumers.

Only an approver may release an order, and only while its status is Approved. Is one mechanism enough?

No. Authorization handles the user-dependent permission; instance feature control handles the state-dependent availability. SAP explicitly separates these concerns: Authorization Control.

Should the OData service implementation calculate the total?

No. Put the invariant in the BO so OData clients, EML consumers, tests, and future service bindings observe the same behavior.
