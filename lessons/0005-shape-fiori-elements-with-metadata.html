Lesson 5 · 50–70 minutes · UI metadata

Shape Fiori elements without moving business rules

Turn the plain read-only preview into a useful List Report and Object Page, add an Items table and value help, and explain why presentation metadata is not backend enforcement.

Prerequisite gate

Start only after Lesson 4's OData V4 UI binding is active and published, $metadata contains both projected entities, and root-to-Item navigation works. UI annotations cannot repair a broken service model.

The tangible win

Produce a List Report with meaningful columns and filters, an Object Page with General and Items sections, and Customer/Product value-help dialogs backed by CDS provider entities.

The implementation remains read-only. This lesson improves the consumer experience without adding create, update, validation, or action behavior.

Step 1 — Allow metadata extensions

Both consumer projections must opt in: 

@Metadata.allowExtensions: true
define root view entity ZC_SalesOrderRequest
  provider contract transactional_query
  as projection on ZI_SalesOrderRequest
{ ... }
@Metadata.allowExtensions: true
define view entity ZC_SalesOrderItem
  provider contract transactional_query
  as projection on ZI_SalesOrderItem
{ ... }

This opt-in lets metadata-extension objects annotate the projections without filling the CDS data definitions with UI layout details.

Step 2 — Annotate the root projection

Create a Metadata Extension for ZC_SalesOrderRequest. Adjust field names only if your activated projection differs. 

@Metadata.layer: #CORE

@UI.headerInfo: {
  typeName:       'Sales Order Request',
  typeNamePlural: 'Sales Order Requests',
  title:       { type: #STANDARD, value: 'RequestNumber' },
  description: { value: 'Status' }
}

annotate entity ZC_SalesOrderRequest with
{
  @UI.facet: [
    { id: 'General', type: #IDENTIFICATION_REFERENCE,
      label: 'General', position: 10 },
    { id: 'Items', type: #LINEITEM_REFERENCE,
      label: 'Items', position: 20, targetElement: '_Items' }
  ]

  @UI: {
    lineItem:       [ { position: 10, importance: #HIGH } ],
    identification: [ { position: 10 } ],
    selectionField: [ { position: 10 } ]
  }
  RequestNumber;

  @UI: {
    lineItem:       [ { position: 20, importance: #HIGH } ],
    identification: [ { position: 20 } ],
    selectionField: [ { position: 20 } ]
  }
  SoldToParty;

  @UI: {
    lineItem:       [ { position: 30, importance: #HIGH } ],
    identification: [ { position: 30 } ],
    selectionField: [ { position: 30 } ]
  }
  Status;

  @UI: {
    lineItem:       [ { position: 40, importance: #MEDIUM } ],
    identification: [ { position: 40 } ]
  }
  TotalAmount;

  @UI.hidden: true
  RequestUUID;
}

The Items facet targets the redirected _Items composition. The child entity's @UI.lineItem annotations determine the columns inside that table.

Step 3 — Annotate the Item projection

Create a second Metadata Extension:

@Metadata.layer: #CORE

@UI.headerInfo: {
  typeName:       'Sales Order Item',
  typeNamePlural: 'Sales Order Items',
  title: { type: #STANDARD, value: 'Product' }
}

annotate entity ZC_SalesOrderItem with
{
  @UI: {
    lineItem:       [ { position: 10, importance: #HIGH } ],
    identification: [ { position: 10 } ]
  }
  Product;

  @UI: {
    lineItem:       [ { position: 20, importance: #HIGH } ],
    identification: [ { position: 20 } ]
  }
  RequestedQuantity;

  @UI: {
    lineItem:       [ { position: 30, importance: #MEDIUM } ],
    identification: [ { position: 30 } ]
  }
  UnitPrice;

  @UI: {
    lineItem:       [ { position: 40, importance: #HIGH } ],
    identification: [ { position: 40 } ]
  }
  NetAmount;

  @UI.hidden: true
  ItemUUID;

  @UI.hidden: true
  RequestUUID;
}

Keep QuantityUnit and TransactionCurrency in the projection even if you do not give them separate columns. Their semantic relationships let the UI interpret quantity and amount fields correctly.

Step 4 — Add Customer and Product value help

Value help belongs on the relevant element in the CDS data definition—not in the metadata extension. Use the provider entities that actually exist in your system. 

// In ZC_SalesOrderRequest
@Consumption.valueHelpDefinition: [ {
  entity: { name: 'ZI_CustomerReference', element: 'CustomerID' },
  useForValidation: true
} ]
SoldToParty,
// In ZC_SalesOrderItem
@Consumption.valueHelpDefinition: [ {
  entity: { name: 'ZI_ProductReference', element: 'ProductID' },
  useForValidation: true
} ]
Product,

The provider must be available to the OData service. Depending on the ABAP release and value-help pattern, it may appear automatically or need explicit exposure. Verify the generated $metadata; if necessary, add the providers to the service definition: 

expose ZI_CustomerReference as Customers;
expose ZI_ProductReference  as Products;

Value help assists selection and can validate against a lookup provider. It does not replace the base BO invariant that a Submitted order must reference an acceptable Customer and Product.

Step 5 — Verify metadata before appearance

  1. Activate both projections and both metadata extensions.
  2. Activate the updated service definition if provider exposure changed.
  3. Refresh or republish according to your system's binding workflow.
  4. Open $metadata and find UI line-item/facet annotations.
  5. Find the Customer and Product value-list metadata.
  6. Open the Fiori Elements preview.
  7. Confirm List Report columns and filters.
  8. Open one Object Page and confirm the Items table.
  9. Open Customer and Product value help and select an entry.

Capture before/after screenshots plus the relevant metadata fragment. The screenshot proves presentation; metadata proves which backend contract produced it.
