Lesson 16 · 120–150 minutes · SAP SD pricing internals

Trace a price from business context to calculated result

Learn the condition technique as two technical pipelines: first SAP selects a pricing procedure; then each procedure step searches for, calculates, and stores a pricing element.

Prerequisite and tangible win

Begin after you can separate category determination from category definition. Review the Lesson 15 recap if you cannot yet diagnose from stored result back to configuration.

By the end: when a Sales Order price or discount is missing or wrong, you can identify the selected pricing procedure, trace one condition type through every attempted access, inspect the calculation result, and classify the failure without guessing.

The business problem

A final item value can contain a base price, discounts, surcharges, freight, taxes, and statistical values. The condition technique lets SAP select these price elements from reusable condition records and combine them in a controlled calculation sequence. SAP's current overview is Condition Technique and Pricing.

Pricing has two different questions: where did the rate come from? and how did that rate contribute to the result? The access sequence answers the first; the pricing procedure and condition controls answer the second.

The complete runtime in two pipelines

Pipeline A — select the pricing procedure

Sales Organization
+ Distribution Channel
+ Division
+ Document Pricing Procedure  ← from sales document type
+ Customer Pricing Procedure  ← from sold-to sales-area data
─────────────────────────────────────────────────────────

SAP describes these inputs as Sales Area, document pricing procedure, and customer pricing procedure in Introducing the Condition Technique.

Pipeline B — execute every procedure step

Pricing procedure
  └─ step/counter
      └─ condition type
          └─ access sequence
              ├─ access 10 → condition table → valid record?
              ├─ access 20 → condition table → valid record?
              └─ access 30 → condition table → valid record?
                    ↓
              rate + scale + base + formula
                    ↓
              condition value → subtotal → item net value

SAP repeats Pipeline B for each condition type in the procedure. An access normally moves from a more specific key to a more general key until a valid record is found or the search ends.

If the wrong pricing procedure was selected, inspecting a missing PR00 condition record may waste time: you may be looking inside the wrong procedure. Always prove Pipeline A first.

Pipeline B, layer 1: pricing procedure

A procedure row is identified by a step and counter. It can contain a condition type and controls such as:

  • Requirement: whether the row should be processed.
  • From/to or alternative base: which prior values form the calculation base.
  • Alternative calculation formula: how the condition value is calculated.
  • Subtotal: where an intermediate result is stored for later use.
  • Mandatory: whether the condition must be present.
  • Manual: whether automatic access is bypassed and a user must enter it.
  • Statistical: display or analysis relevance without ordinary contribution to net value.
  • Account/accrual keys: downstream account-determination meaning where applicable.

The step order is calculation order, not search priority. Search priority belongs inside the access sequence of one condition type.

Pipeline B, layer 2: condition type

A condition type represents a pricing concept. Common illustrative standard examples include PR00 for a base price, K004 for a material discount, K007 for a customer discount, KF00 for freight, and MWST for output tax. Exact use is configuration-specific.

In V/06, controls can include calculation type, plus/minus sign, group-condition behavior, header/item applicability, scales, manual-entry rules, and an assigned access sequence. A common table landmark is T685. 

Condition type = meaning and calculation behavior
Condition record = actual rate for a valid business key and period

Pipeline B, layer 3: access sequence and condition tables

An access sequence is a prioritized list of accesses. Each access points to a condition table, whose fields form a search key. 

Illustrative price search

Access 10: Sales Org + Channel + Customer + Material
           → most specific negotiated price

Access 20: Sales Org + Channel + Price List + Material
           → segment/list price

Access 30: Sales Org + Channel + Material
           → general material price

V/07 maintains access sequences. Common technical landmarks include T682I for accesses and T682Z for access fields. Condition tables can be created, changed, and displayed with classic transactions V/03, V/04, and V/05. Generated application tables commonly use names such as Axxx, where the number and key structure depend on the configured condition table.

“Record not found” does not always mean no record exists. The access may use different key values, the requirement may skip the access, the record may be outside its validity period, or an earlier access may have stopped the search.

Pipeline B, layer 4: condition records

Condition records are pricing master data. In applicable classic systems, use VK11, VK12, and VK13 to create, change, and display records. The fields requested by these transactions depend on the condition type's access sequence and condition tables.

In classic persistence, generated Axxx tables connect a business key to a condition-record number; KONH and KONP are familiar condition-record landmarks. Treat this as implementation knowledge, not as authorization to update the tables or expose them as a clean-core contract.

Rate, base, and value are different

Condition rate  = maintained amount or percentage
Condition base  = amount or quantity to which the rate applies
Condition value = calculated contribution in this document

Runtime persistence in SAP S/4HANA

A Sales Order contains a pricing-document reference commonly exposed as VBAK-KNUMV. In SAP S/4HANA, document pricing-result rows are persisted in PRCD_ELEMENTS. SAP's conversion guidance states that KONV no longer has the old persistence role; do not design new S/4HANA database reads as if it were still the pricing-result table. 

VBAK-KNUMV
    =
PRCD_ELEMENTS-KNUMV
  ├─ KPOSN  document item
  ├─ STUNR  pricing procedure step
  ├─ ZAEHK  counter within the step
  ├─ KSCHL  condition type
  ├─ KAWRT  condition base value
  ├─ KBETR  condition rate
  ├─ KWERT  calculated condition value
  ├─ KPEIN  pricing unit
  ├─ KMEIN  condition unit
  ├─ KSTAT  statistical indicator
  ├─ KINAK  inactive indicator/reason context
  ├─ KNUMH  source condition-record reference where applicable
  └─ KHERK  condition origin

A pricing element is identified at a finer grain than the Sales Order item: pricing document + item + procedure step + counter. Joining only by order or item can multiply rows and inflate totals.

Master versus result: condition records are reusable pricing master data; PRCD_ELEMENTS represents the pricing result captured for a particular business document.

End-to-end missing-price diagnostic

  1. Capture the grain. Record Sales Order and item plus expected condition type, rate, and value.
  2. Check item eligibility. Confirm the item category allows pricing and the item is not rejected or otherwise excluded.
  3. Prove procedure selection. Record Sales Area, document pricing procedure, customer pricing procedure, and resulting pricing procedure.
  4. Open Pricing Analysis. Find the condition type and distinguish absent, skipped, not found, inactive, and calculated states.
  5. Trace the access. Use Technical View to record the actual access fields and values—not the values you expected.
  6. Inspect the record. Verify key, validity/pricing date, rate, currency, pricing unit, unit of measure, and scales.
  7. Validate calculation. Compare base, rate, formula, sign, conversion, rounding, statistical/inactive status, and resulting value.
  8. Inspect persistence only when useful. Correlate the order pricing-document reference with the correct pricing-result grain.
  9. Widen after standard logic. Then check manual changes, condition exclusion, copy control/repricing, enhancements, external pricing, or integration data.

Pricing can change between order and billing

A billing document may copy pricing or perform some form of repricing, depending on the pricing type configured in copy control and the process. Therefore: 

Sales Order pricing result ≠ guaranteed Billing pricing result

Compare the document flow, pricing dates, source/target pricing elements, and copy-control pricing type before calling a difference a defect. SAP explains this boundary in the “New Pricing and Pricing Types” section of Introducing the Condition Technique.

The Sales Order OData V4 API exposes item pricing elements through SalesOrderItemPricingElement and the _ItemPricingElement navigation. SAP documents fields such as condition type, procedure step/counter, rate, currency, and base quantity in Sales Order Item Pricing Element. Supported operations and fields remain release-specific.

Transfer the idea to your RAP portfolio

Your current deriveAmounts determination can calculate a simple quantity × unit-price result. It does not reproduce SD pricing. A transparent portfolio boundary would be: 

Custom portfolio logic
  RequestedQuantity × UnitPrice → NetAmount
  Σ Item.NetAmount              → Request.TotalAmount

Standard SD integration boundary
  Pricing procedure + conditions + released Sales API
  → externally determined pricing elements and totals

If you later integrate standard Sales pricing, keep the adapter deep: accept a business pricing request, call a released capability, and return normalized pricing elements. Do not duplicate SAP's condition tables and procedure engine inside custom RAP behavior.

Your technical trace exercise

Scenario: Item 10 should receive a customer/material price, but SAP uses a more general material price. The displayed rate is also unexpected for 120 EA.

  1. Write every Pipeline A input and the determined procedure.
  2. Locate the expected price condition type in the procedure and record its step/counter.
  3. Draw three accesses from most specific to most general.
  4. List the runtime key values you expect Pricing Analysis to show for access 10.
  5. Give three reasons why a customer/material record could exist but not be selected.
  6. Explain how the general record could be selected after access 10 fails.
  7. Check rate, pricing unit, order quantity, and scale before calculating the condition value.
  8. Write the expected PRCD_ELEMENTS grain and the fields that prove the result.
  9. Explain which evidence would justify checking enhancement code.
