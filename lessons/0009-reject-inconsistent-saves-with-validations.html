Lesson 9 · 120–150 minutes · Validations and messages

Let drafts be incomplete, but never activate invalid business data

Check Customer and Product references, reject non-positive Item quantities, and return field-specific messages. Learn how Prepare, failed, reported, and state areas turn a business invariant into a safe draft activation.

Prerequisite gate

Start only after Lesson 8 passes: quantity and unit-price changes derive Item net amounts, Item create/delete recalculates the root total, and draft discard/activation preserves the correct state.

  • ZI_CustomerReference exposes CustomerID.
  • ZI_ProductReference exposes ProductID.
  • Customer and Product lookup entities are readable in your ABAP release.
  • The root draft Prepare action already exists from Lesson 7.
  • Use disposable draft data for every negative-path test.

The tangible win

Keep an incomplete or invalid Request as a draft, but prevent it from becoming active. Enter quantity zero, an unknown Product, or an unknown Customer; activation fails, Fiori highlights the responsible field, and the active database state remains unchanged. Correct the value and activate successfully.

Four concepts that must stay separate

This lesson uses validations because incomplete draft data is useful while the user works, but invalid data must not become active.

Step 1 — Declare the validations

Merge these lines into the Lesson 8 base BDEF. Preserve all existing operations, draft actions, determinations, fields, associations, ETags, and mappings. 

define behavior for ZI_SalesOrderRequest alias SalesOrderRequest
  // keep the existing Lesson 8 header
{
  validation validateCustomer on save
    { create; field SoldToParty; }

  draft determine action Prepare
  {
    validation validateCustomer;
    validation SalesOrderItem~validateProduct;
    validation SalesOrderItem~validateQuantity;
  }

  // keep actions, determination, fields, association, and mapping
}

define behavior for ZI_SalesOrderItem alias SalesOrderItem
  // keep the existing Lesson 8 header
{
  validation validateProduct on save
    { create; field Product; }

  validation validateQuantity on save
    { create; field RequestedQuantity; }

  // keep determination, fields, association, and mapping
}

A validation is always on save. Its trigger declaration records which changes make the previous validation result obsolete. Because this BO uses draft, root Prepare explicitly includes both root and child validations.

Step 3 — Implement the smallest rule first: positive quantity

Business flow: read current Items → clear the old quantity-message state → find invalid quantities → fail those Items → report an error attached to RequestedQuantity. 

METHOD validateQuantity.
  " 1. Read current draft/active Item values for the triggered keys
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderItem
      FIELDS ( RequestedQuantity )
      WITH CORRESPONDING #( keys )
      RESULT DATA(items).

  LOOP AT items INTO DATA(item).
    " 2. Clear an older state message from this same validation area
    APPEND VALUE #(
      %tky        = item-%tky
      %state_area = 'VALIDATE_QUANTITY'
    ) TO reported-SalesOrderItem.

    " 3. Check the business invariant
    IF item-RequestedQuantity <= 0.
      " 4. FAILED controls the save result
      APPEND VALUE #(
        %tky = item-%tky
      ) TO failed-SalesOrderItem.

      " 5. REPORTED explains the failure to the consumer
      APPEND VALUE #(
        %tky        = item-%tky
        %state_area = 'VALIDATE_QUANTITY'
        %msg        = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text     = 'Requested quantity must be greater than zero' )
        %element-RequestedQuantity = if_abap_behv=>mk-on
      ) TO reported-SalesOrderItem.
    ENDIF.
  ENDLOOP.
ENDMETHOD.

Read the quantity code as business behavior

CodeLogic meaningBusiness/UI effect
READ ENTITIES ... IN LOCAL MODERead the current BO state for the requested keys.The check sees the quantity currently stored in the draft, not only active SQL data.
item-%tkyCarry the complete transactional key, including draft identity.The message binds to the correct active/draft Item.
State-area-only rowReplace the prior result owned by VALIDATE_QUANTITY.Correcting quantity clears the old error instead of leaving a stale message.
failed-SalesOrderItemMark this Item inconsistent.Activation/save is rejected; the aggregate is not partially persisted.
reported-SalesOrderItemReturn an instance-bound message.The consumer learns what must be corrected.
%element-RequestedQuantityAssociate the message with one field.Fiori can highlight the quantity field.

A message alone is not the rejection. failed blocks persistence; reported communicates why. Fill both for an error that must reject save.

Step 4 — Validate the root Customer reference

Business flow: read every affected Request → collect its Customer IDs → query the reusable Customer reference CDS once → reject missing or unknown buyers. 

METHOD validateCustomer.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( SoldToParty )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests).

  IF requests IS NOT INITIAL.
    SELECT FROM ZI_CustomerReference
      FIELDS CustomerID
      FOR ALL ENTRIES IN @requests
      WHERE CustomerID = @requests-SoldToParty
      INTO TABLE @DATA(valid_customers).
  ENDIF.

  LOOP AT requests INTO DATA(request).
    APPEND VALUE #(
      %tky        = request-%tky
      %state_area = 'VALIDATE_CUSTOMER'
    ) TO reported-SalesOrderRequest.

    IF request-SoldToParty IS INITIAL OR
       NOT line_exists(
         valid_customers[ CustomerID = request-SoldToParty ] ).

      APPEND VALUE #(
        %tky = request-%tky
      ) TO failed-SalesOrderRequest.

      APPEND VALUE #(
        %tky        = request-%tky
        %state_area = 'VALIDATE_CUSTOMER'
        %msg        = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text     = |Customer { request-SoldToParty } does not exist| )
        %element-SoldToParty = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
    ENDIF.
  ENDLOOP.
ENDMETHOD.

The guard IF requests IS NOT INITIAL is required before FOR ALL ENTRIES. Querying once for all requested IDs avoids a database lookup inside every loop iteration. If your lookup entity or released field names differ, use ADT completion and adjust only the provider names—not the validation flow.

Step 5 — Apply the same flow to Product

Product validation belongs to the Item handler, but the algorithm is the same as Customer validation. 

METHOD validateProduct.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderItem
      FIELDS ( Product )
      WITH CORRESPONDING #( keys )
      RESULT DATA(items).

  IF items IS NOT INITIAL.
    SELECT FROM ZI_ProductReference
      FIELDS ProductID
      FOR ALL ENTRIES IN @items
      WHERE ProductID = @items-Product
      INTO TABLE @DATA(valid_products).
  ENDIF.

  LOOP AT items INTO DATA(item).
    APPEND VALUE #(
      %tky        = item-%tky
      %state_area = 'VALIDATE_PRODUCT'
    ) TO reported-SalesOrderItem.

    IF item-Product IS INITIAL OR
       NOT line_exists( valid_products[ ProductID = item-Product ] ).

      APPEND VALUE #( %tky = item-%tky )
        TO failed-SalesOrderItem.

      APPEND VALUE #(
        %tky        = item-%tky
        %state_area = 'VALIDATE_PRODUCT'
        %msg        = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text     = |Product { item-Product } does not exist| )
        %element-Product = if_abap_behv=>mk-on
      ) TO reported-SalesOrderItem.
    ENDIF.
  ENDLOOP.
ENDMETHOD.

Fiori value help improves entry, but this backend validation protects OData API calls, EML callers, alternate projections, and clients that never opened the value-help dialog.

Optional extension — Validate requested delivery date

Only do this step if RequestedDeliveryDate already exists or you intentionally add it to persistence, interface CDS, projection CDS, draft shape, mapping, and UI metadata. Do not paste a validation for a field your BO does not contain. 

// Root BDEF
validation validateDeliveryDate on save
  { create; field RequestedDeliveryDate; }

draft determine action Prepare
{
  // keep the three core validations
  validation validateDeliveryDate;
}
METHOD validateDeliveryDate.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( RequestedDeliveryDate )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests).

  DATA(today) = cl_abap_context_info=>get_system_date( ).

  LOOP AT requests INTO DATA(request).
    APPEND VALUE #(
      %tky        = request-%tky
      %state_area = 'VALIDATE_DELIVERY_DATE'
    ) TO reported-SalesOrderRequest.

    IF request-RequestedDeliveryDate IS INITIAL OR
       request-RequestedDeliveryDate < today.
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.

      APPEND VALUE #(
        %tky        = request-%tky
        %state_area = 'VALIDATE_DELIVERY_DATE'
        %msg        = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text     = 'Requested delivery date cannot be in the past' )
        %element-RequestedDeliveryDate = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
    ENDIF.
  ENDLOOP.
ENDMETHOD.

Step 6 — Activate and test the save boundary

  1. Activate the base BDEF.
  2. Generate and implement the three validation methods.
  3. Activate the behavior pool and BDEF again.
  4. Refresh the service metadata/application if required.
  5. Create a new Request draft with a valid Customer.
  6. Create an Item with a valid Product and quantity zero.
  7. Confirm the draft can exist, then attempt activation.
  8. Record the failed activation, message, highlighted field, and unchanged active data.
  9. Correct quantity and activate successfully.
  10. Repeat with unknown Customer and Product IDs.
