Lesson 7 · 90–120 minutes · Draft and concurrency

Let users pause safely without allowing lost updates

Persist work in progress in draft tables, keep active data unchanged until activation, and use managed locks plus entity and total ETags to protect concurrent editing of the Sales Order Request aggregate.

Prerequisite gate

Start only after Lesson 6 passes in ADT: both behavior definitions activate, root CRUD works, an Item can be created through _Items, and managed UUID numbering produces persisted keys.

  • Export or record the current active-table definitions before changing them.
  • Use disposable test records for concurrency tests.
  • Arrange a second browser profile or second test user if your system permits it.
  • Keep the OData V4 UI binding from Lesson 4.

The tangible win

Start editing a Request, close the application, reopen the saved draft, and either discard or activate it. Then demonstrate that a second user or a stale OData request cannot silently overwrite a newer active version.

This lesson protects editing mechanics. Calculating totals, validating business rules, and implementing Submit remain later lessons.

Five states and controls that must not be confused

MechanismQuestion it answersLifetime/scope
Transactional bufferWhere are changes held during the current RAP transaction?Temporary; cleared when the transaction finishes.
Draft persistenceHow can unfinished work survive requests or sessions?Persisted in separate draft tables until discard or activation.
Managed lockWho may modify the aggregate right now?Pessimistic, exclusive control rooted at the lock master.
Entity ETagIs the entity version being modified still the version the client read?Optimistic check for an OData modification.
Total ETagDid any active entity in the draft BO change while an edit draft was held?Optimistic comparison for the whole BO during draft resume/transition.

Predict the draft lifecycle

Active Request→ Edit →Draft copy→ autosave →Draft table→ Activate →Active table

Edit copies active data into draft persistence. Prepare will later run selected determinations and validations. Activate transfers the accepted draft state to active persistence. Discard removes the draft without changing active data, and Resume re-establishes editing after the durable lock has expired.

Step 1 — Add administrative fields to active persistence

Add these fields to zsor_request. Use the equivalent released data elements available in your ABAP release if the names differ: 

local_created_by       : abp_creation_user;
local_created_at       : abp_creation_tstmpl;
local_last_changed_by  : abp_locinst_lastchange_user;
local_last_changed_at  : abp_locinst_lastchange_tstmpl;
last_changed_at        : abp_lastchange_tstmpl;

Add the entity-local administrative fields to zsor_item:

local_created_by       : abp_creation_user;
local_created_at       : abp_creation_tstmpl;
local_last_changed_by  : abp_locinst_lastchange_user;
local_last_changed_at  : abp_locinst_lastchange_tstmpl;

LocalLastChangedAt will be each entity's local ETag. Root LastChangedAt will be the aggregate's total ETag. Keep them as separate fields because they answer different concurrency questions.

Step 3 — Draft-enable the base behavior

Extend the Lesson 6 BDEF. The following shows the new concurrency declarations and the affected existing lines; preserve your complete field mappings and controls. 

managed implementation in class ZBP_I_SALESORDERREQUEST unique;
strict ( 2 );
with draft;

define behavior for ZI_SalesOrderRequest alias SalesOrderRequest
  persistent table zsor_request
  draft table zsor_req_d
  lock master
  total etag LastChangedAt
  etag master LocalLastChangedAt
{
  create;
  update;
  delete;

  draft action Edit;
  draft action Activate optimized;
  draft action Discard;
  draft action Resume;
  draft determine action Prepare;

  association _Items { create; with draft; }

  field ( numbering : managed, readonly ) RequestUUID;
  field ( readonly ) TotalAmount,
                     LocalCreatedBy, LocalCreatedAt,
                     LocalLastChangedBy, LocalLastChangedAt,
                     LastChangedAt;

  mapping for zsor_request
  {
    // Keep every Lesson 6 mapping, then add:
    LocalCreatedBy      = local_created_by;
    LocalCreatedAt      = local_created_at;
    LocalLastChangedBy  = local_last_changed_by;
    LocalLastChangedAt  = local_last_changed_at;
    LastChangedAt       = last_changed_at;
  }
}

define behavior for ZI_SalesOrderItem alias SalesOrderItem
  persistent table zsor_item
  draft table zsor_item_d
  lock dependent by _SalesOrderRequest
  etag master LocalLastChangedAt
{
  update;
  delete;

  association _SalesOrderRequest { with draft; }

  field ( numbering : managed, readonly ) ItemUUID;
  field ( readonly ) RequestUUID, NetAmount,
                     LocalCreatedBy, LocalCreatedAt,
                     LocalLastChangedBy, LocalLastChangedAt;

  mapping for zsor_item
  {
    // Keep every Lesson 6 mapping, then add:
    LocalCreatedBy      = local_created_by;
    LocalCreatedAt      = local_created_at;
    LocalLastChangedBy  = local_last_changed_by;
    LocalLastChangedAt  = local_last_changed_at;
  }
}

Do not paste the abbreviated mapping over your full Lesson 6 mapping. Merge the added fields into it. Also keep your existing mandatory : create declarations.

Draft Edit has an instance-feature hook. If your ADT release requires a handler method during activation, use Quick Fix to generate the FOR INSTANCE FEATURES method and temporarily return Edit as enabled for every requested key: 

result = VALUE #( FOR key IN keys
  ( %tky = key-%tky
    %action-Edit = if_abap_behv=>fc-o-enabled ) ).

Do not invent the method signature; let ADT generate it. A later feature-control lesson will replace the unconditional result with a status-dependent rule.

Step 4 — Generate the draft tables with ADT

  1. After adding with draft and each draft table declaration, place the cursor on the draft-table error.
  2. Use Quick Fix to generate zsor_req_d and zsor_item_d.
  3. Confirm that each generated table contains the CDS alias fields and "%admin" : include sych_bdl_draft_admin_inc;.
  4. Activate both draft tables and then the base BDEF.

Let ADT derive draft tables from the actual CDS entities. Do not maintain them by hand and do not read or modify them with direct SQL. Regenerating an existing draft table can overwrite its definition, so inspect pending changes before accepting a regeneration.

Step 5 — Project draft behavior

Replace the Lesson 6 behavior projection with the draft-aware form:

projection;
strict ( 2 );
use draft;

define behavior for ZC_SalesOrderRequest alias SalesOrderRequest
  use etag
{
  use create;
  use update;
  use delete;

  use action Edit;
  use action Activate;
  use action Discard;
  use action Resume;
  use action Prepare;

  use association _Items { create; with draft; }
}

define behavior for ZC_SalesOrderItem alias SalesOrderItem
  use etag
{
  use update;
  use delete;

  use association _SalesOrderRequest { with draft; }
}

Draft actions are supplied by the RAP draft runtime. Do not implement custom action methods unless you explicitly declare additional implementation or dynamic feature control. Later lessons will attach validations and determinations to Prepare.

Step 6 — Activate from persistence outward

  1. Activate the two active tables.
  2. Activate both interface entities and both projections.
  3. Generate/activate the draft tables.
  4. Activate the base BDEF and behavior pool.
  5. Activate the behavior projection.
  6. Refresh or republish the OData V4 UI binding as your system requires.
  7. Inspect $metadata for ETag and draft capabilities.

In the service metadata and runtime requests, expect draft-related technical state such as active/draft indicators. These are generated by the framework; they are not new business fields in your tables.

Step 7 — Prove the draft lifecycle

  1. Open an existing active Request and choose Edit.
  2. Change a harmless field and navigate away without activating.
  3. Verify through the normal UI or OData draft contract that a draft exists; do not query the draft table directly.
  4. Confirm that the active CDS/table value has not changed.
  5. Reopen the application and continue the draft.
  6. Discard it and confirm that active data remains unchanged.
  7. Repeat the edit, then activate/save it.
  8. Confirm that active persistence now contains the new value and the timestamps changed.
  9. Create a new Request draft, close/reopen it, then activate it.

Step 8 — Prove concurrency rather than only describing it

TestProcedureExpected evidence
Exclusive editUser A edits a Request; User B attempts to edit the same active Request.User B cannot silently obtain a competing exclusive edit draft.
Stale entity ETagCapture an entity response and ETag, change and activate the entity elsewhere, then issue a permitted modification using the old If-Match.The service rejects the stale modification—commonly with HTTP 412—instead of overwriting the newer version.
Total ETag reasoningRecord the total ETag before and after changing either the root or an Item.The root total ETag represents change to the whole active aggregate.
Expired-lock resumeIf your environment and timeout permit, resume an old edit draft after active data changed.Total-ETag comparison prevents unsafe continuation. Otherwise document this as an unexecuted environment-limited test.

Use the browser network trace or an authorized OData client for the stale-ETag test. Never modify production or shared customer data for a portfolio experiment.
