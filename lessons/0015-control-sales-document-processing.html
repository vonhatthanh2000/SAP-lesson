Lesson 15 · 90–105 minutes · SAP SD document control

Control one Sales Order at three levels

Trace how the sales document type controls the transaction, the item category controls each product line, and the schedule-line category controls fulfillment behavior—then diagnose why SAP selected them.

Prerequisite and tangible win

Begin after you can distinguish Sales Order header, item, and schedule-line grain. Review the Lesson 14 recap if those levels are not yet automatic.

By the end: given a Sales Order item that is not priced, confirmed, or delivery relevant, you can reconstruct the two configuration lookups and decide whether the error is in the selected category, its control settings, or its master-data inputs.

The complete control chain

Header: Sales document type
  │
  ├─ with material item-category group, usage, higher-level item
  ▼
Item: Item category
  │
  ├─ with material/plant MRP type
  ▼
Schedule line: Schedule-line category
  │
  └─ controls fulfillment participation

These are not three names for the same thing. Each is a configuration switch at a different business grain. SAP summarizes this division in How Sales Documents Are Controlled.

Level Question it answers Examples of influence
Sales document type What commercial transaction is this? Document category, defaults, blocks, checks, follow-on document proposals
Item category How does this particular line participate? Pricing, billing relevance, business-data differences, text/material behavior, schedule lines
Schedule-line category How does this dated quantity participate in logistics? Delivery relevance, requirements transfer, ATP, movement type, procurement

1. Sales document type: control the transaction

The sales document type applies at header level. It distinguishes processes such as inquiry, quotation, standard order, returns, or contracts. Its settings can supply defaults and influence document category, delivery or billing blocks, checks, and proposed subsequent document types. See SAP Learning's Configuring a Sales Document Type.

A document type provides the overall process context; it does not decide every item and schedule behavior by itself. Those decisions are delegated through category determination.

In classic on-premise/private-edition configuration, VOV8 is the familiar maintenance transaction, TVAK is a configuration landmark, and the selected type appears as VBAK-AUART. In public cloud, use the available configuration activities rather than expecting classic transactions.

2. Item category: control one line

The item category lets the same material behave differently in different transactions. It can govern pricing, billing relevance, whether item business data can differ from the header, whether the line is a material or text item, the incompletion procedure, and whether schedule lines are permitted. SAP Learning gives the current overview in Configuring an Item Category.

How SAP proposes it

Sales document type
+ Item category group from the material sales data
+ Item usage
+ Higher-level item category
──────────────────────────────────────────────────
= Proposed item category

In the simplest stock-material case, usage and higher-level item may be blank. They become important for special lines such as text, free-goods, BOM, or subitems. This is why “the material determines the item category” is incomplete: the document and item context also participate.

Classic landmarks are VOV7/TVAP for the category definition and VOV4/T184 for the determination assignment. The material's item-category group is commonly inspected in sales-area material data (MVKE-MTPOS), and the determined value is stored on the order item as VBAP-PSTYV.

3. Schedule-line category: control fulfillment

First, the item category must allow schedule lines. The selected schedule-line category then controls whether the dated quantity is relevant for delivery, requirements transfer and availability check, which movement type supports later goods movement, and whether a purchase requisition or delivery block is involved. See Configuring Schedule Line Categories.

How SAP proposes it

1. Try: Item category + material/plant MRP type
2. Fallback: Item category + blank MRP type
──────────────────────────────────────────────
= Proposed schedule-line category

The assignment can also define permitted alternatives. SAP documents this exact two-step lookup in Assigning Schedule Line Categories.

Classic landmarks are VOV6/TVEP for the category definition and VOV5/TVEPZ for the assignment. The MRP type is commonly inspected at material/plant level as MARC-DISMM; the result appears as VBEP-ETTYP.

SAP then reads the settings of the selected categories. If the item is unexpectedly not priced, inspect the item-category result and definition. If the quantity is not transferred to requirements or not delivery relevant, inspect the schedule-line result and definition—after confirming that the item allows schedule lines.

Four traps that matter in interviews and incidents

Determination ≠ definition

The assignment selects a category. The category definition says what the selected category does.

Movement type ≠ posting

A movement type in schedule-line configuration prepares later goods-movement behavior; saving the order does not itself prove goods issue occurred.

Delivery relevance has levels

For scheduled material items, schedule-line control is central. The item-category delivery-relevance indicator specifically supports items without schedule lines.

Configuration ≠ transaction data

Changing a configuration rule changes processing logic. It is not the same as editing one Sales Order, and its impact must be tested and transported deliberately.

Technical Consultant diagnostic flow

  1. Capture the symptom and grain. In VA03, record the Sales Order, item, and schedule line plus expected versus actual behavior.
  2. Read the selected results. Note VBAK-AUART, VBAP-PSTYV, and VBEP-ETTYP.
  3. Reconstruct item-category inputs. Check document type, MVKE-MTPOS in the correct sales area, item usage, and higher-level item category.
  4. Verify the lookup. Compare those inputs with the VOV4 assignment, then inspect the selected category in VOV7.
  5. Reconstruct schedule-line inputs. Check item category and MARC-DISMM for the correct material and plant.
  6. Verify exact and fallback lookups. Inspect VOV5, then the selected schedule-line control in VOV6.
  7. Widen only after standard inputs are explained. Then inspect copy control, master-data gaps, other configuration, or enhancements.

Never repair the symptom by directly editing configuration or transaction tables. Use authorized configuration activities, document the rationale, test dependent flows, and transport through the landscape. For clean-core extensions, prefer released APIs and CDS contracts over direct table dependencies.

Do not confuse SD determination with RAP determination

Term Meaning Typical implementation
SD category determination Select a configured category from several business inputs Customizing lookup such as item- or schedule-line-category assignment
RAP determination Automatically derive or update BO data after declared triggers Behavior definition plus behavior-pool implementation
RAP validation Reject inconsistent BO state with messages On-save or other supported validation trigger

In your portfolio, a simplified RequestType, ItemProcessingType, and FulfillmentPolicy could express the three scopes. Do not claim they reproduce standard SD configuration. If you integrate with standard Sales, keep SAP's control model behind a released integration boundary instead of duplicating its rules in custom RAP code.

Your 35-minute trace exercise

Scenario: one normal stock item receives the expected item category, but no requirement is transferred and no quantity is confirmed.

  1. Draw the three control levels and write the stored result field for each.
  2. List all four item-category determination inputs.
  3. List both schedule-line lookup attempts in their correct order.
  4. Separate evidence that the wrong category was selected from evidence that the correct category has unsuitable settings.
  5. Explain why checking only the Material and Sales Order type is insufficient.
  6. Explain why finding movement type 601 in configuration is not evidence that PGI occurred.
  7. Translate the control scopes—not SAP's exact logic—into your RAP portfolio vocabulary.
