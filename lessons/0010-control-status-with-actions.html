Lesson 10 · 120–150 minutes · Actions and status invariants

Turn status changes into explicit business commands

Replace direct status editing with guarded Submit, Release, and PutOnHold instance actions. Model legal transitions, reject illegal commands, update the RAP buffer through local EML, and return the changed Request to every consumer.

Prerequisite gate

Start only after Lesson 9 passes: invalid Customer, Product, and quantity values reject activation with field-specific messages, while a corrected draft activates successfully.

  • A valid Request with at least one valid Item can become active.
  • Status exists on the root interface and projection entities.
  • The root behavior pool from Lessons 8–9 activates.
  • The OData V4 UI behavior projection is available for adding actions.
  • Use disposable active Requests for transition tests.

The tangible win

Activate a valid Open Request, submit it, release it, and prove that an illegal transition—such as releasing an Open Request or changing a Released Request—fails with a business message. The consumer never enters a status code directly.

Technical draft state is not business status

ConceptMeaningOwner
Draft/activeWhether the editable version is staged or official.RAP draft runtime through %is_draft.
Open/Submitted/Released/On HoldWhere the Request is in its business process.The Sales Order Request BO through Status.

The portfolio workflow used here is: create and edit a draft, activate it as an Open Request, then execute business actions on the active instance. RAP actions can also target draft instances when their transactional keys identify a draft, but keep this first state-machine test on active data so the two lifecycles do not become confused.

Lesson 9 already protects Customer, Product, and quantity during activation. Submit owns the new cross-entity rule that a Request must have at least one Item. Do not duplicate every existing save validation inside every action.

Step 1 — Define stable status constants

Add constants to the root local handler class. Use the actual type and stored codes agreed for your project; do not scatter character literals through action methods. 

CONSTANTS:
  BEGIN OF request_status,
    open      TYPE c LENGTH 1 VALUE 'O',
    submitted TYPE c LENGTH 1 VALUE 'S',
    released  TYPE c LENGTH 1 VALUE 'R',
    on_hold   TYPE c LENGTH 1 VALUE 'H',
  END OF request_status.

In a production design, prefer an appropriate released domain/data element or typed constant. The important idea is one canonical map from meaningful names to persisted codes.

Step 2 — Make Status BO-owned and declare the commands

Merge these declarations into the Lesson 9 root BDEF:

define behavior for ZI_SalesOrderRequest alias SalesOrderRequest
  // keep the existing managed/draft header
{
  field ( readonly ) Status;

  determination setInitialStatus on modify { create; }

  action Submit result [1] $self;
  action Release result [1] $self;
  action PutOnHold result [1] $self;

  // keep CRUD, draft actions, validations, determinations,
  // associations, fields, and mapping from earlier lessons
}

These are instance actions by default: each incoming key identifies a Request on which the command is executed. result [1] $self promises one updated Request entity as the result for each successful action instance.

Step 3 — Initialize every created Request as Open

This recalls Lesson 8's determination pattern. Because Status is externally read-only, the BO assigns its initial value automatically. 

METHOD setInitialStatus.
  MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      UPDATE FIELDS ( Status )
      WITH VALUE #(
        FOR key IN keys
        ( %tky   = key-%tky
          Status = request_status-open )
      ).
ENDMETHOD.

This is a determination because initialization is automatic. Submit and Release are actions because a business user explicitly requests those transitions.

Step 4 — Generate action method contracts

Use ADT Quick Fix rather than typing derived signatures manually:

METHODS Submit FOR MODIFY
  IMPORTING keys FOR ACTION SalesOrderRequest~Submit
  RESULT result.

METHODS Release FOR MODIFY
  IMPORTING keys FOR ACTION SalesOrderRequest~Release
  RESULT result.

METHODS PutOnHold FOR MODIFY
  IMPORTING keys FOR ACTION SalesOrderRequest~PutOnHold
  RESULT result.

The generated action handler also receives implicit failed and reported response structures.

Submit business flow

Submit keys→Read status and Items→Guard transition→Update accepted keys→Return $self
  1. RAP supplies the transactional keys selected by the consumer.
  2. The action reads current Request status and composition links.
  3. Open/On Hold and at least one Item are required.
  4. Illegal instances go to failed with a reported message.
  5. Only accepted instances enter the local EML update table.
  6. The method reads those updated instances and wraps each one in %param because the action returns $self.
  7. RAP's outer transaction owns save or rollback; the handler never commits.

Step 5 — Implement Submit

METHOD Submit.
  " 1. Read the current Requests and their Item links
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( Status )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests)
    ENTITY SalesOrderRequest BY \_Items
      FIELDS ( ItemUUID )
      WITH CORRESPONDING #( keys )
      RESULT DATA(items)
      LINK DATA(item_links).

  " 2. Collect only Requests that satisfy Submit invariants
  DATA requests_to_update TYPE TABLE FOR UPDATE
    ZI_SalesOrderRequest.

  LOOP AT requests INTO DATA(request).
    " Legal source-state check
    IF request-Status <> request_status-open AND
       request-Status <> request_status-on_hold.
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.
      APPEND VALUE #(
        %tky = request-%tky
        %msg = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text = |Request cannot be submitted from status { request-Status }| )
        %element-Status = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
      CONTINUE.
    ENDIF.

    " Cross-entity readiness check
    IF NOT line_exists(
      item_links[ source-%tky = request-%tky ] ).
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.
      APPEND VALUE #(
        %tky = request-%tky
        %msg = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text = 'A Request must contain at least one Item before submission' )
      ) TO reported-SalesOrderRequest.
      CONTINUE.
    ENDIF.

    APPEND VALUE #(
      %tky   = request-%tky
      Status = request_status-submitted
    ) TO requests_to_update.
  ENDLOOP.

  " 3. Apply only accepted transitions to the current BO transaction
  IF requests_to_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        UPDATE FIELDS ( Status )
        WITH requests_to_update.

    " 4. Read the changed state promised by result [1] $self
    READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        ALL FIELDS
        WITH CORRESPONDING #( requests_to_update )
        RESULT DATA(updated_requests).

    result = VALUE #(
      FOR updated_request IN updated_requests
      ( %tky   = updated_request-%tky
        %param = updated_request )
    ).
  ENDIF.
ENDMETHOD.

The items result is required by the read-by-association operation even though this method only uses item_links to answer “does at least one child exist?”. Keep the code simple first; optimize only after a measured need.

Read Submit as business decisions

Code conceptBusiness meaningRuntime effect
keysRequests on which the consumer invoked Submit.Supports one or many selected instances.
request-%tkyExact active/draft transactional instance.The read, failure, update, message, and result refer to the same instance.
Source-state conditionOnly Open or On Hold may enter Submitted.An illegal command never reaches the update table.
item_linksEvidence that the aggregate contains a child Item.An empty Request fails before status changes.
failedThis action instance was rejected.RAP does not perform the requested transition for that key.
reportedExplain which transition invariant failed.Consumer receives an actionable message; it is not a persistent log.
Local EML updateThe BO, not the consumer, owns the status code.Updates the current transactional state without committing.
%paramReturn the changed Request promised by $self.Consumer receives Submitted status and other current fields.

Step 6 — Implement Release with the same pattern

Business rule: only a Submitted Request with a positive derived total may become Released. 

METHOD Release.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( Status TotalAmount )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests).

  DATA requests_to_update TYPE TABLE FOR UPDATE
    ZI_SalesOrderRequest.

  LOOP AT requests INTO DATA(request).
    IF request-Status <> request_status-submitted.
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.
      APPEND VALUE #(
        %tky = request-%tky
        %msg = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text = 'Only a Submitted Request can be released' )
        %element-Status = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
      CONTINUE.
    ENDIF.

    IF request-TotalAmount <= 0.
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.
      APPEND VALUE #(
        %tky = request-%tky
        %msg = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text = 'A Request with a non-positive total cannot be released' )
        %element-TotalAmount = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
      CONTINUE.
    ENDIF.

    APPEND VALUE #(
      %tky   = request-%tky
      Status = request_status-released
    ) TO requests_to_update.
  ENDLOOP.

  IF requests_to_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        UPDATE FIELDS ( Status )
        WITH requests_to_update.

    READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        ALL FIELDS
        WITH CORRESPONDING #( requests_to_update )
        RESULT DATA(updated_requests).

    result = VALUE #(
      FOR updated_request IN updated_requests
      ( %tky   = updated_request-%tky
        %param = updated_request ) ).
  ENDIF.
ENDMETHOD.

Step 7 — Implement Put On Hold

Business rule: Open or Submitted may move to On Hold. Released is terminal in this lesson, and invoking Hold on an already-held Request is rejected rather than silently succeeding. 

METHOD PutOnHold.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( Status )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests).

  DATA requests_to_update TYPE TABLE FOR UPDATE
    ZI_SalesOrderRequest.

  LOOP AT requests INTO DATA(request).
    IF request-Status <> request_status-open AND
       request-Status <> request_status-submitted.
      APPEND VALUE #( %tky = request-%tky )
        TO failed-SalesOrderRequest.
      APPEND VALUE #(
        %tky = request-%tky
        %msg = new_message_with_text(
          severity = if_abap_behv_message=>severity-error
          text = |Request cannot be put on hold from status { request-Status }| )
        %element-Status = if_abap_behv=>mk-on
      ) TO reported-SalesOrderRequest.
      CONTINUE.
    ENDIF.

    APPEND VALUE #(
      %tky   = request-%tky
      Status = request_status-on_hold
    ) TO requests_to_update.
  ENDLOOP.

  IF requests_to_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        UPDATE FIELDS ( Status )
        WITH requests_to_update.

    READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderRequest
        ALL FIELDS
        WITH CORRESPONDING #( requests_to_update )
        RESULT DATA(updated_requests).

    result = VALUE #(
      FOR updated_request IN updated_requests
      ( %tky   = updated_request-%tky
        %param = updated_request ) ).
  ENDIF.
ENDMETHOD.

Step 8 — Expose the actions to this consumer

Add the actions to the root behavior projection:

projection;
strict ( 2 );
use draft;

define behavior for ZC_SalesOrderRequest alias SalesOrderRequest
  use etag
{
  // keep CRUD, draft actions, and association exposure
  use action Submit;
  use action Release;
  use action PutOnHold;
}

The base BDEF owns and implements the commands. The behavior projection only decides that this service consumer may invoke them. Do not reimplement action logic in the projection.

Expected UI behavior before Lesson 11

All three action buttons may remain visible or enabled regardless of current status. That is acceptable for this lesson because the action handlers still reject illegal transitions. Lesson 11 will add instance feature control so the UI advertises only currently valid operations, plus side effects where immediate rereads are needed.

Feature control improves guidance; it does not replace the action's backend invariant. Authorization later answers a separate question: whether this user may perform a transition that is otherwise legal.

Close ADT and answer one question at a time:

  • What does result [1] $self promise?
  • Why does an action receive a table of keys rather than one UUID?
  • How does Submit find whether a Request contains at least one Item?
