Lesson 8 · 90–120 minutes · Determinations and local EML

Make derived amounts belong to the business object

Calculate each Item's net amount and the Request's aggregate total whenever quantity, price, or Item membership changes. Keep the rule inside the base BO so every UI, API, and EML consumer gets the same result.

Prerequisite gate

Start only after Lesson 7 passes: the draft-enabled Request and Item BDEFs activate, a draft can be resumed and activated, and ETags protect stale changes.

  • Use disposable Requests and Items for calculation tests.
  • Keep the complete Lesson 7 mappings and administrative fields.
  • Confirm the Item contains RequestUUID, RequestedQuantity, UnitPrice, NetAmount, and TransactionCurrency.
  • Confirm the root contains TotalAmount and TransactionCurrency.

The tangible win

Enter quantity 3 and unit price 25.00. RAP derives Item NetAmount = 75.00 and recalculates the Request total. Change the quantity, add another Item, and delete an Item; the aggregate total follows the draft state without consumer-supplied totals.

This lesson derives values. It does not yet reject zero quantities, missing products, invalid status transitions, or submission without Items. Those are validation rules in Lesson 9.

Choose the correct rule mechanism

QuestionMechanismSales Order example
Should RAP derive or change data automatically?DeterminationCalculate NetAmount and TotalAmount.
Should inconsistent data be rejected with a message?ValidationReject quantity less than or equal to zero.
Did the user explicitly request a business transition?ActionSubmit or release a Request.
Should a field or operation be available for this instance?Feature controlDisable Item edits after submission.
Should Fiori reread affected values immediately?Side effectRefresh the root total after an Item change.

A determination owns the formula. A side effect does not calculate anything; it tells a UI when to request the already-calculated value again.

Predict the runtime before coding

Item create/change/delete→deriveAmounts→Item NetAmount→internal recalculateTotal→Request TotalAmount
  1. The consumer changes determining fields, never the derived fields.
  2. RAP invokes the Item determination in the interaction phase.
  3. The handler reads current transactional state with local EML.
  4. For Items that still exist, it derives net amount and currency.
  5. It invokes one private root operation for every affected Request.
  6. The root operation reads all remaining Items and writes the sum.
  7. Save or draft activation persists the consistent buffer state.

Step 1 — Preserve parent identity on delete

Make RequestUUID part of the Item CDS business key as well as ItemUUID. Keep the to-parent association on that field. The exact source syntax depends on your current entity, but the exposed key shape must be equivalent to: 

define view entity ZI_SalesOrderItem
  as select from zsor_item as Item
  association to parent ZI_SalesOrderRequest as _SalesOrderRequest
    on $projection.RequestUUID = _SalesOrderRequest.RequestUUID
{
  key Item.request_uuid as RequestUUID,
  key Item.item_uuid    as ItemUUID,
      // existing Item fields and associations
}

Project both fields as keys in ZC_SalesOrderItem. The globally unique Item UUID still identifies the Item, but carrying the parent UUID in the RAP key means a delete trigger can identify its affected root even after the Item is absent from the buffer.

This changes the draft entity key. Let ADT regenerate the disposable Item draft-table definition from the activated CDS shape, inspect the proposed change, and recreate test drafts. Do not hand-edit or query draft tables. In a real deployed system, changing a BO key requires an explicit compatibility and data migration decision.

Step 2 — Declare one deterministic orchestration

Merge these declarations into the Lesson 7 base BDEF. Preserve all draft, ETag, mapping, association, and administrative declarations. 

define behavior for ZI_SalesOrderRequest alias SalesOrderRequest
  // keep Lesson 7 header
{
  // keep Lesson 7 operations, draft actions, fields, and mapping

  internal action recalculateTotal;

  field ( mandatory : create, readonly : update ) TransactionCurrency;
  field ( readonly ) TotalAmount;
}

define behavior for ZI_SalesOrderItem alias SalesOrderItem
  // keep Lesson 7 header
{
  // keep Lesson 7 operations, association, fields, and mapping

  field ( numbering : managed, readonly ) ItemUUID;
  field ( readonly ) RequestUUID, NetAmount, TransactionCurrency;
  field ( mandatory : create ) Product, RequestedQuantity,
                               QuantityUnit, UnitPrice;

  determination deriveAmounts on modify
    { create; delete; field RequestedQuantity, UnitPrice; }
}

The Item currency is derived from its Request and cannot drift from the aggregate currency. The root currency is fixed after creation; changing it later would require an explicit repricing/conversion policy rather than silently relabeling stored amounts.

Do not split net and total calculation into two determinations with the same triggers. RAP does not guarantee determination execution order. One orchestration first updates Item amounts and then calls the root recalculation, so the total cannot accidentally read the old net amount.

Step 3 — Generate handler method signatures

  1. Activate the BDEF far enough for ADT to report the missing implementations.
  2. Use Quick Fix on recalculateTotal and deriveAmounts.
  3. Generate both methods in the existing Lesson 7 behavior pool.
  4. Do not type the derived method signatures from memory.

The generated declarations should express these contracts:

METHODS recalculateTotal FOR MODIFY
  IMPORTING keys FOR ACTION SalesOrderRequest~recalculateTotal.

METHODS deriveAmounts FOR DETERMINE ON MODIFY
  IMPORTING keys FOR SalesOrderItem~deriveAmounts.

Depending on how ADT organized your behavior pool, the methods may be in separate local handler classes for root and child. That is normal; the BDEF remains the contract.

Step 4 — Derive Item values, then invoke the root operation

Implement deriveAmounts using the structure below. Let ADT completion resolve your release's generated table types and component spelling. 

METHOD deriveAmounts.
  " Read only Items that still exist after the triggering modification.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderItem
      FIELDS ( RequestedQuantity UnitPrice NetAmount
               TransactionCurrency RequestUUID )
      WITH CORRESPONDING #( keys )
      RESULT DATA(items).

  " Parent keys remain available for create, update, and delete because
  " RequestUUID is part of the Item business key.
  DATA(request_keys) = VALUE TABLE FOR ACTION IMPORT
    ZI_SalesOrderRequest~recalculateTotal(
      FOR key IN keys
      ( RequestUUID = key-RequestUUID
        %is_draft   = key-%is_draft ) ).

  SORT request_keys BY RequestUUID %is_draft.
  DELETE ADJACENT DUPLICATES FROM request_keys
    COMPARING RequestUUID %is_draft.

  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( TransactionCurrency )
      WITH CORRESPONDING #( request_keys )
      RESULT DATA(requests).

  LOOP AT items ASSIGNING FIELD-SYMBOL(<item>).
    ASSIGN requests[
      RequestUUID = <item>-RequestUUID
      %is_draft   = <item>-%is_draft ] TO FIELD-SYMBOL(<request>).
    IF sy-subrc <> 0.
      CONTINUE.
    ENDIF.

    <item>-TransactionCurrency = <request>-TransactionCurrency.
    <item>-NetAmount =
      <item>-RequestedQuantity * <item>-UnitPrice.
  ENDLOOP.

  IF items IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
      ENTITY SalesOrderItem
        UPDATE FIELDS ( NetAmount TransactionCurrency )
        WITH CORRESPONDING #( items )
      REPORTED DATA(item_reported).
  ENDIF.

  MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      EXECUTE recalculateTotal
      FROM request_keys
    REPORTED DATA(total_reported).

  reported = CORRESPONDING #( DEEP item_reported ).
  reported = CORRESPONDING #( DEEP BASE ( reported ) total_reported ).
ENDMETHOD.

Treat this as a guided implementation shape, not blind paste. Generated EML derived-type syntax can differ by ABAP release. Keep the algorithm invariant: read current Items → derive fields → update locally → invoke each affected root once.

Step 5 — Sum the current aggregate state

Implement the private root action. It must read through the root composition so it sees the current draft/transactional state, not a stale SQL snapshot. 

METHOD recalculateTotal.
  READ ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      FIELDS ( TotalAmount )
      WITH CORRESPONDING #( keys )
      RESULT DATA(requests)
    ENTITY SalesOrderRequest BY \_Items
      FIELDS ( NetAmount )
      WITH CORRESPONDING #( keys )
      RESULT DATA(items)
      LINK DATA(item_links).

  LOOP AT requests ASSIGNING FIELD-SYMBOL(<request>).
    CLEAR <request>-TotalAmount.

    LOOP AT item_links ASSIGNING FIELD-SYMBOL(<link>)
      WHERE source-%tky = <request>-%tky.
      ASSIGN items[ KEY entity
        %tky = <link>-target-%tky ] TO FIELD-SYMBOL(<item>).
      IF sy-subrc = 0.
        <request>-TotalAmount += <item>-NetAmount.
      ENDIF.
    ENDLOOP.
  ENDLOOP.

  MODIFY ENTITIES OF ZI_SalesOrderRequest IN LOCAL MODE
    ENTITY SalesOrderRequest
      UPDATE FIELDS ( TotalAmount )
      WITH CORRESPONDING #( requests )
    REPORTED DATA(update_reported).

  reported = CORRESPONDING #( DEEP update_reported ).
ENDMETHOD.

Starting from zero makes the operation idempotent: running it twice against the same Item state produces the same total. The action is internal, so it is reusable inside the BO but is not a public consumer operation and is not projected.

Why IN LOCAL MODE is essential here

PropertyConsequence in this handler
Reads the BO's current transactional stateThe calculation includes unsaved draft Item changes.
Uses the base BO contractThe behavior pool is not coupled to one projection or OData service.
Allows implementation-internal updatesRAP can write fields that are read-only to external consumers.
Does not perform a commitThe outer RAP transaction still owns save or rollback.

Local mode is not permission to bypass business consistency casually. Use it inside trusted BO implementation code for the object's own derived state; never issue COMMIT WORK from the handler.

  4. Generate, implement, and activate the behavior pool methods.
  5. Activate the behavior projection; do not project the internal action.
  6. Refresh or republish the OData V4 UI binding as required.

Record the Item values, root total, and draft/active state before and after each operation. If delete leaves a stale total, first verify that RequestUUID is part of the Item key and that delete is a determination trigger.

Expected UI behavior before the side-effect lesson

The transactional state can be correct while the object-page header still displays an old total. A draft-enabled Fiori client does not reread every field after every input change. Use save, navigation, or manual refresh to verify the backend value in this lesson. A later side-effect lesson will make Item changes cause the root total to be requested immediately.

Do not “fix” a stale display by moving the formula into UI code. First prove the buffer value through RAP, then separately teach the UI which affected property to reread.
