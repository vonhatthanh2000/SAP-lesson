Lesson 6 · 70–90 minutes · Managed behavior

Turn the read-only model into a transactional business object

Declare managed CRUD for the Sales Order Request aggregate, create Items only through their parent, expose the behavior to the UI service, and trace one change from the transactional buffer to the database.

Prerequisite gate

Start after Lessons 3–5 activate in ADT: the interface composition and projected redirection work, the OData V4 UI binding is published, and the preview can read a Request with its Items.

  • The root and Item database tables activate.
  • The root and Item keys are UUID-compatible raw(16) fields.
  • Your actual entity and association names are consistent; do not mix ZI_/ZR_ or _Item/_Items.
  • You can restore your test data if delete testing removes it.

The tangible win

Create, edit, and delete a Sales Order Request in the Fiori Elements preview; save it; then add, edit, and delete an Item through the Request's Items section.

This is the first transactional slice, not the final portfolio version. It intentionally has no draft, ETag, custom validation, total calculation, Submit action, or authorization implementation.

Two behavior contracts

ArtifactResponsibilityExample
Base behavior definitionDefines the reusable BO's complete transactional contract.Managed persistence, CRUD, numbering, lock dependency, field control.
Behavior projectionSelects which existing behavior this consumer may use.use create, use update, and Item create-by-association.
Behavior poolContains custom handler/saver logic when declared behavior requires implementation.Later validations, determinations, actions, and authorization.

Managed does not mean “there is no behavior.” It means the RAP managed provider supplies the transactional buffer and standard persistence for operations you declare. No custom CRUD methods are needed for this lesson.

Predict the write path

Fiori save→projected behavior→base behavior→transactional buffer→managed save sequence→tables

During the interaction phase, changes belong to the transactional buffer. The managed provider persists the consistent buffer state in the save sequence. Declaring create does not mean every field change is immediately written to the table.

Step 1 — Create the base behavior definition

Create a Behavior Definition from your root interface entity and choose implementation type Managed. The skeleton below uses the ZI_ and _Items names used in the recent lessons. Replace them once with your activated names. 

managed implementation in class ZBP_I_SALESORDERREQUEST unique;
strict ( 2 );

define behavior for ZI_SalesOrderRequest alias SalesOrderRequest
  persistent table zsor_request
  lock master
{
  create;
  update;
  delete;

  association _Items { create; }

  field ( numbering : managed, readonly ) RequestUUID;
  field ( mandatory : create ) SoldToParty, TransactionCurrency;
  field ( readonly ) TotalAmount;

  mapping for zsor_request
  {
    RequestUUID        = request_uuid;
    SoldToParty        = sold_to_party;
    Status             = status;
    TotalAmount        = total_amount;
    TransactionCurrency = transaction_currency;
  }
}

define behavior for ZI_SalesOrderItem alias SalesOrderItem
  persistent table zsor_item
  lock dependent by _SalesOrderRequest
{
  update;
  delete;

  association _SalesOrderRequest;

  field ( numbering : managed, readonly ) ItemUUID;
  field ( readonly ) RequestUUID, NetAmount;
  field ( mandatory : create ) Product, RequestedQuantity, QuantityUnit,
                               UnitPrice, TransactionCurrency;

  mapping for zsor_item
  {
    ItemUUID            = item_uuid;
    RequestUUID         = request_uuid;
    Product             = product;
    RequestedQuantity   = requested_quantity;
    QuantityUnit        = quantity_unit;
    UnitPrice           = unit_price;
    NetAmount           = net_amount;
    TransactionCurrency = transaction_currency;
  }
}

Complete the mapping for every persistent element in your real interface entity, including fields such as RequestNumber if you added them. Managed numbering works here only when the numbered key has UUID type raw(16).

Read each declaration as a design decision

DeclarationMeaning
managedRAP supplies standard CRUD buffering and persistence.
strict ( 2 )Activates current BDL consistency and best-practice checks.
persistent tableIdentifies where managed persistence stores the entity.
lock masterThe root owns the aggregate lock.
lock dependent byItem locking resolves through the parent Request.
association _Items { create; }Enables child creation through an existing parent.
numbering : managedRAP assigns the UUID during create.
readonly/mandatory : createRestricts consumer writes or requires presence on create; it does not validate business meaning.
mapping forConnects CDS element names to differently named table fields.

Notice that the child has no standalone create. An Item has no independent lifecycle, so it is created through _Items on its parent.

Step 2 — Create the behavior pool

  1. Activate the base behavior definition.
  2. Use the ADT quick fix on the implementation class name to create ZBP_I_SALESORDERREQUEST.
  3. Activate the behavior pool.
  4. Do not add handwritten create, update, delete, or save methods.

The class artifact is the home for behavior you will implement later. Standard managed CRUD and save are already supplied by the framework.

Step 3 — Project the behavior

Create a Behavior Definition from the root projection entity and choose implementation type Projection: 

projection;
strict ( 2 );

define behavior for ZC_SalesOrderRequest alias SalesOrderRequest
{
  use create;
  use update;
  use delete;

  use association _Items { create; }
}

define behavior for ZC_SalesOrderItem alias SalesOrderItem
{
  use update;
  use delete;

  use association _SalesOrderRequest;
}

The projection does not implement CRUD again. Each use exposes behavior already defined by the base BO. A future API projection could deliberately omit use delete while reusing the same base behavior.

Step 4 — Activate and refresh the service

  1. Activate the base behavior definition and behavior pool.
  2. Activate the behavior projection.
  3. Activate the CDS projections and service definition if ADT reports dependent changes.
  4. Refresh or republish the OData V4 UI binding as required by your system.
  5. Inspect $metadata and confirm that insert, update, and delete restrictions now permit the projected operations.
  6. Open a fresh Fiori Elements preview.

Step 5 — Prove the transaction

  1. Create a Request with Customer and Currency, then save it.
  2. Confirm that RAP generated RequestUUID.
  3. Edit one permitted header field and save again.
  4. Open the saved Request and create an Item through the Items section.
  5. Enter Product, quantity/unit, price, and currency; then save.
  6. Confirm that RAP generated ItemUUID and linked RequestUUID.
  7. Edit and then delete that Item through the parent.
  8. Create disposable test data and verify root delete; do not delete evidence you cannot restore.
  9. Use table/CDS preview only after save to prove persistence.

Record one before-save screenshot, one successful save, and the persisted row. Explain that UI state is not database evidence until the save sequence completes.

Run three failure-oriented checks

CheckExpected resultWhat it proves
Leave a statically mandatory field empty.The consumer/runtime refuses completion and identifies the missing field.BDEF field control reached the consumer.
Try to type a UUID or TotalAmount.The field is not editable.Static read-only behavior is exposed.
Look for standalone Item creation.Items are created through the parent, not as independent roots.Behavior follows composition ownership.

These checks do not prove business consistency. Quantity greater than zero, Product eligibility, total calculation, and valid status transitions require later determinations and validations.
