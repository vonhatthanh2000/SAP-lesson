OpenSAP Travel under the microscope

Follow one concrete RAP application from persistence to Fiori, then transfer its structure—not its obsolete details—to the Sales Order portfolio.

Use this repository carefully

SAP's own repository warning says the associated 2020 course is no longer available and the exercises are not up to date. Use it to understand artifact relationships and runtime flow. Use current SAP Help, RAP100, and RAP110 as the implementation baseline.

Concrete outdated detail: the sample creates an OData V2 UI binding because V4 was not yet available in that exercise. For the new portfolio, use OData V4 where supported; the historical note appears in Week 2 Unit 6.

The domain

Travel root

Owns trip dates, agency/customer references, currency, booking fee, total price, status, and audit information.

Booking child

Belongs to one Travel and holds flight selection, customer, price, currency, and child identity.

Independent references

Agency, Customer, Carrier, Connection, Flight, and Currency exist outside the Travel lifecycle.

The root declares Booking as a composition while Agency, Customer, and Currency are associations. The child declares its association to parent plus independent references.

Trace B — Invoke Accept Travel

Accept button→projected action→base action contract→handler→transactional buffer→save
  1. The metadata extension places the acceptTravel action on the UI.
  2. The behavior projection explicitly exposes the base action.
  3. The base behavior definition declares the managed BO, action, determinations, and validations.
  4. The handler updates TravelStatus using EML in local mode, then reads the buffer to build the action result.
  5. Managed RAP owns standard persistence. The separate external EML example makes the interaction/save boundary visible by separating MODIFY ENTITIES and COMMIT ENTITIES.

The sample action sets Accepted status but is not a production-grade release policy. For Sales Order Release, enforce allowed pre-state and authorization in the backend; feature control only guides the client.

Known traps in this sample

  • Do not copy the OData V2 choice into a new project; it reflects the 2020 environment.
  • The repository stores service-binding creation instructions, not a serialized binding source artifact.
  • Do not copy authorization helpers that force the result to allowed for testing.
  • Do not copy the adjusted exercise DCL that replaces authorization conditions with an unrestricted condition.
  • Do not treat maximum-ID-plus-one logic as safe, unique, or gap-free numbering.
  • Do not infer production architecture from an instructional Travel domain.
  • Do not let UI feature control replace backend invariants or authorization.
