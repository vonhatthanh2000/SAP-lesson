Follow RAP through real SAP code

These commit-pinned links connect every architectural notion in Lesson 1 to first-party SAP sample code. Read them as one request path; do not copy the Travel application file by file.

How to read each sample

For every link, answer three questions: what contract is declared? what does RAP generate? and what logic remains for the developer?

Use RAP110's Travel as the analogue of SalesOrderRequest, and Booking as the analogue of Item. Transfer the structure and runtime reasoning—not the field names or tutorial business rules.

Trail A — Persistence to client

Notion Official sample What to inspect Your transfer question
Persistence Travel table · Booking table Separate active tables, keys, administrative fields, amounts, currencies, and parent identity. Which fields belong to Order and which to Item?
CDS root and composition Root and _Booking composition · Child and to parent The composition originates at the root; the child points back to its parent. Together they define the BO topology. Should an Item exist independently of its Order Request?
Managed behavior contract Base BDEF header · Child behavior and dependency managed, draft and persistence tables, locks, ETags, authorization mode, numbering, mapping, create-by-association, and dependent lock/authorization. Which responsibilities are framework-owned, and which are your code?
Behavior implementation Saver and handler structure · Handler method contracts The local handler class declares only the breakouts required by the BDEF. The saver is a separate lifecycle participant. Why is there no ordinary controller class?
Projection CDS Transactional projection · Redirected composition provider contract transactional_query, projection source, and redirection from projected root to projected child. Which internal fields should the portfolio UI never expose?
Projection behavior Projected operations, actions, draft, and side effects The consumer contract explicitly reuses selected base behavior. Notice that an action is not automatically public merely because it exists in the base BO. Should every internal action be reachable over OData?
Fiori elements metadata Header and facets · Action buttons UI annotations describe presentation and action affordances; they do not implement the business rule. If the button disappeared, could an EML consumer still violate the invariant?
Service definition Exposed entities A small protocol-neutral exposure list. There is no business implementation here. Which projections belong in your portfolio service?
OData V4 service binding Binding repository metadata The binding object points to the service definition and records the OData V4 binding. In normal work, inspect and publish this object in ADT rather than hand-editing its XML. Why can one service definition support different bindings?

Trail B — Put business logic in the right mechanism

Notion Declaration Implementation or metadata What to learn
Determination Rules and actions in the base BDEF calculateTotalPrice and helper · child triggers parent recalculation Observe trigger declaration, aggregate reads, child-to-parent navigation, and idempotent derived values. This is the closest sample for item changes recalculating an order total.
Validation validateDates Follow the path from current buffered state to failed and reported. Adapt it to requested-date and non-empty-order invariants.
Action acceptTravel · createTravel aggregate action The first is a clear state change; the second creates root and child together. Adapt the first to Release, then explain its allowed pre-state.
Instance feature control Feature-controlled fields/actions get_instance_features Return operation/field availability from current instance state. Adapt it so Release is enabled only for an Approved order.
Side effects Root declarations · Child-to-root dependencies Exposure in projection behavior Side effects tell an OData client what to reread; they do not calculate the value. Adapt child quantity/price changes to refresh item and header totals.
Authorization Authorization declaration Empty RAP110 authorization seam · concrete instance-response example Caution: RAP110 declares the hook but implements no real permission decision. The cheat-sheet sample shows allowed/unauthorized response mechanics, but its toy field rule is not role security. Use SAP's Authorization Control documentation with your real authorization-object design.

Trail C — Transaction, save, and proof

Read from the buffer

Inspect RAP100's EML read example. Identify the BO contract being consumed and the response structures.

Create and commit

Inspect the EML create example. Locate mapped, failed, reported, and the commit boundary.

Custom save breakouts

RAP110 demonstrates adjust_numbers and save_modified. Standard managed persistence is runtime-generated, so an ordinary application INSERT/UPDATE is intentionally absent.

ABAP Unit through EML

Inspect test-double setup, then the action, commit, and assertions.

Active-reading exercise

  1. Open the RAP110 root CDS, base BDEF, projection CDS/BDEF, service definition, and binding in that order.
  2. Draw a line from each artifact to the next. Label the contract crossing the line.
  3. Open acceptTravel. Predict the buffer change before reading the method body.
  4. Open validateDates. Find exactly where failure identity and user-facing messages separate.
  5. Write a five-row mapping from Travel terms to your Sales Order portfolio terms.

Pass condition: explain why the metadata extension, service definition, and service binding contain no order-release invariant.
